AI 工程避坑指南

记录那些不报错但效果极差的“幽灵 Bug”及其定位过程

💡 为什么需要这份文档？

在 AI 工程（特别是基于大模型开发）中，很多 Bug 不会抛出 Exception，而是表现为“召回率下降”、“回答莫名其妙”、“相似度暴跌”。这份文档记录了我们在教学和开发过程中踩过的真实大坑，以及如何科学地定位这些问题。

案例 1：OpenAIEmbeddings 与兼容 API 的 Tokenizer 冲突

触发场景：使用 LangChain 的 OpenAIEmbeddings 调用非 OpenAI 模型（如智谱、DeepSeek） 症状：检索相似度无故暴跌，RAG 门控失效 发现时间：Week 2 (Lesson 0006)

1. 症状表现

在使用手写代码（原生的 openai Python 客户端）时，检索同一段文档的相似度得分为 0.62；但迁移到 LangChain，使用 langchain-chroma + OpenAIEmbeddings 后，在底层数据库完全一致的情况下，同一查询的相似度暴跌至 0.26。因为相似度太低，导致 0.5 的防幻觉门控被错误触发，正常问题也被拒答。

2. 科学定位过程

我们没有盲目猜测，而是通过编写探针脚本，一步步缩小了包围圈：

  1. 确认不是向量库的问题：
    猜测可能是 ChromaDB 在 LangChain 中的距离计算方式变了。我们打印了 LangChain 取出的原始距离，发现是 0.736（转换相似度刚好是 0.264）。这说明 LangChain 拿到的就是错误的距离，根源在向量本身。
  2. 对比向量数据：
    我们写了一个探针脚本，同时用手写版 OpenAI 客户端和 LangChain 版 OpenAIEmbeddings 对同一句话“什么是编码规范检查？”提取向量，并计算这两个向量的内积（Dot Product）。结果内积只有 0.35——这证明两者虽然调用的都是 https://open.bigmodel.cn/...，但生成的向量完全不一样。
  3. 抓包底层 HTTP 请求：
    为了看清 LangChain 到底往智谱发送了什么，我们开启了 http.client 和 requests 的底层的 DEBUG 模式： 
    import logging
import http.client
http.client.HTTPConnection.debuglevel = 1
logging.getLogger("requests.packages.urllib3").setLevel(logging.DEBUG)
  4. 真相大白：
    在控制台的 HTTP 日志中，我们看到 LangChain 发送的 payload 是：
    {'input': [[6271, 222, 82696, 21043, 31968, 16882, 75486...]]}
    而原生客户端发送的是：
    {'input': ["什么是编码规范检查？"]}
    结论： LangChain 的 OpenAIEmbeddings 默认开启了长度检查，为了截断超长文本，它私下使用了 OpenAI 的 tiktoken 分词器把中文切成了整数数组发了出去。智谱的 API 兼容 OpenAI 格式，所以收到了整数数组没报错，但智谱的词表和 OpenAI 完全不同，于是把这些数字当成了无意义的乱码，最终算出了一个垃圾向量！

3. 解决方案

在初始化 OpenAIEmbeddings 时，必须显式关闭上下文长度检查：

embeddings = OpenAIEmbeddings(
    model="embedding-3", 
    api_key=GLM_KEY, 
    base_url="https://open.bigmodel.cn/api/paas/v4/",
    check_embedding_ctx_length=False  # 关键修复：禁止使用 tiktoken 预分词
)

4. 核心启发

  • AI Bug 往往是“静默失败”的： 乱码生成乱码向量，API 不会报错（200 OK），但业务逻辑彻底崩溃。
  • “兼容”只是接口兼容，不是模型兼容： 各家大模型的 Tokenizer（分词器）是不可互换的。永远不要让 A 厂的 tokenizer 去预处理发给 B 厂模型的数据。
