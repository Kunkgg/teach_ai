图 1：Lesson 8 手写 Tool Calling 流程

这段代码能跑，但如果你要把它用在生产环境，三个问题会冒出来：

  1. 状态管理：messages 列表需要你手动 append，多轮对话时容易漏或错
  2. 可视化：while True + if/else 嵌套深了，流程只存在你脑子里
  3. 人工介入：执行敏感操作前想让人确认？手写循环里很难做

LangGraph 用状态图（StateGraph）解决这三个问题——把 while 循环变成一张可视化的图。

知识 ①：核心心智模型 — Graph = 升级版 while 循环

Lesson 8 的 while True 循环，用 LangGraph 画出来就是这张图：

     ┌─────────┐
     │  START  │
     └────┬────┘
          ▼
   ┌─────────────┐
   │   chatbot    │ ←─────────────────────────┐
   │ （调用 LLM） │                            │
   └──────┬──────┘                            │
          │                                   │
     有 tool_calls?                           │
     ╱          ╲                             │
   Yes          No                            │
    │            │                            │
    ▼            ▼                            │
┌────────┐  ┌────────┐                       │
│ tools  │  │  END   │                       │
│(执行)  │  └────────┘                       │
└───┬────┘                                   │
    └─────────────────────────────────────────┘

图 2：LangGraph StateGraph —— 和 Lesson 8 完全对应

对照表——Lesson 8 的每行代码，都能在 LangGraph 里找到对应：

Lesson 8 手写 LangGraph
while True: Graph 自动循环（tools → chatbot 回边）
if not tool_calls: break tools_condition → 路由到 END
for tc in tool_calls: execute... ToolNode(tools) 自动执行
messages.append(...) 手动追加 add_messages reducer 自动管理
💡 一句话总结

LangGraph 没做新的事——它只是把你已经理解的 Tool Calling 循环，放进了一个结构化的画布里。State 就是你手动维护的 messages 列表。Node 就是你的函数。Edge 就是你的 if/else 分支。

知识 ②：四个新概念

1. State — 图的共享记忆

from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

class State(TypedDict):
    messages: Annotated[list, add_messages]

State 是一个 TypedDict，定义了图里所有节点共享的数据。messages 是最核心的字段——对话历史。

2. Node — 做事的函数

def chatbot(state: State):
    return {"messages": [llm_with_tools.invoke(state["messages"])]}

每个 Node 是一个 Python 函数，接收当前 state，返回一个部分更新（只返回要更新的 key）。

3. Edge — 连接节点

# 固定路径：START → chatbot
graph_builder.add_edge(START, "chatbot")

# 条件路径：chatbot → tools 或 END
graph_builder.add_conditional_edges("chatbot", tools_condition)
  • Normal edge：固定走向，如 tools → chatbot
  • Conditional edge：动态路由，根据 state 决定走向

4. Compile — 编译成可执行图

graph = graph_builder.compile()

编译后得到 CompiledGraph，可以 .invoke() 或 .stream()。

知识 ③：add_messages — 为什么需要 Reducer

这是 LangGraph 最容易踩的坑：

写法 Node 返回 {"messages": [new_msg]} 的效果
messages: list（无 reducer） 覆盖整个列表 → 对话历史丢失！
messages: Annotated[list, add_messages] 追加到已有列表 → 历史完整保留 ✅
⚠️ 面试高频考点

「LangGraph 的 State 里 Annotated[list, add_messages] 有什么作用？」答：add_messages 是一个 reducer 函数，它让每个 node 返回的消息追加到已有列表，而不是覆盖。没有它，每个 node 执行后之前的对话历史会丢失。

知识检验

Q1: State 中 Annotated[list, add_messages] 的 add_messages 做了什么？

Q2: tools_condition 在什么情况下会路由到 END？

Q3: 相比手写 while 循环，StateGraph 最关键的优势是什么？

卡住了？点开看完整答案

14_langgraph_hello.py 三处空白的答案 
# ① State 的 messages 字段：用 Annotated + add_messages
class State(TypedDict):
    messages: Annotated[list, add_messages]

# ② 添加条件边：chatbot 之后根据 tool_calls 决定走向
graph_builder.add_conditional_edges("chatbot", tools_condition)

# ③ 调用 graph：传入 state 格式的字典
result = graph.invoke({"messages": [HumanMessage(content=question)]})

① 为什么用 Annotated[list, add_messages]？ add_messages 是 reducer 函数，让每个 node 返回的 {"messages": [new_msg]} 追加到已有列表，而不是覆盖。没有它，每次 node 执行后之前的对话历史就丢了。

② 为什么用 tools_condition 而不是手写路由函数？ tools_condition 是 LangGraph 预置的路由函数，它检查最后一条 AIMessage 是否有 tool_calls——有就返回 "tools"，没有就返回 END。和 Lesson 8 的 if not ai_msg.tool_calls: break 完全对应。

③ 为什么输入是 {"messages": [...]}？ graph.invoke() 接收的输入格式必须和 State 的结构匹配。State 有一个 messages 字段，所以输入字典的 key 也是 "messages"。

延伸：create_react_agent — 一行搞定

LangGraph 提供了一个快捷函数 create_react_agent，它把上面的 State 定义 + Node 定义 + Edge 连接 + 编译全部封装成一行：

from langgraph.prebuilt import create_react_agent

agent = create_react_agent(llm, tools)
result = agent.invoke({"messages": [HumanMessage(content=question)]})

但你要先理解手动搭建的过程——面试一定会问「create_react_agent 内部做了什么？」你现在能答：它创建了一个 StateGraph，定义了 chatbot 和 tools 两个 node，用 tools_condition 做条件路由，用 add_messages 管理状态。
