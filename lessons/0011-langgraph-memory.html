Lesson 0011

给 Agent 装上记忆：Checkpointer 与 thread_id

同一个 Agent，有人记得住上文，有人失忆 —— 差别就在这两样东西

⏱️ 约 25–35 分钟 LangGraph · Memory 📅 Week 3

问题：你的 Agent 是金鱼

回去在 14_langgraph_hello.py 里连问两次试试：graph.invoke() 第一次问"auth-service 有多少违规"，第二次问"那它的可信分数呢"——第二次它会完全不知道"它"是谁。因为每次 invoke() 都从空白 State 开始，上一次的 messages 没有任何人替你留着。

这不是玩具问题。可信看板的用户就是这么说话的：

"auth-service 有多少条违规？" → "那它的分数呢？" → "比 user-service 好还是差？"

第二句的"它"、第三句的"刚才"都依赖前文。Week 1 你在 qa.py 里其实解决过这个问题——自己维护一个全局 messages 列表，每轮 append 后整体传给 LLM。能用，但只能一个进程一个会话，重启全丢。今天看 LangGraph 怎么把这件事做成生产级能力：两个新名词，Checkpointer 和 thread_id，就这两样。

概念 ①: Checkpointer —— 每一步都存一份 State 快照

给你的图挂上一个 checkpointer，LangGraph 就会在每个超步（superstep，即每个 node 执行一轮）结束后，把当时的整个 State 序列化存起来。下次同一个会话再 invoke()，它先把存好的 State 取出来，把你的新消息合并进去，再继续跑——这就是记忆的全部原理。

from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()
graph = graph_builder.compile(checkpointer=checkpointer)   # ← 就多这一个参数

呼应你上一课读源码的发现：checkpoint 存的正是那个被 add_messages reducer 管理的 State。分工很清楚——reducer 决定「新消息怎么合并进 State」，checkpointer 决定「合并后的 State 怎么保存」。所以如果你忘了写 Annotated[list, add_messages]，checkpointer 也救不了你：它忠实地每步存档，但每次存的都是被覆盖后的残缺历史。

名字考古（读源码习惯持续生效）

老教程里叫 MemorySaver——你现在装的是 langgraph 1.2.10，打开 langgraph/checkpoint/memory/__init__.py 看最后一行：

# line 33: class InMemorySaver(...)      ← 1.x 的正式类名
# line 41: "Only use `InMemorySaver` for debugging or testing purposes."
# line 631: MemorySaver = InMemorySaver  # Kept for backwards compatibility

MemorySaver 只是别名。docstring 那句警告也很诚实：内存版进程一退就没了，生产环境换 SqliteSaver（单机文件）或 PostgresSaver（生产标配），都在独立的包里（langgraph-checkpoint-sqlite / langgraph-checkpoint-postgres，需要时 uv add 即可）。关键设计：checkpointer 是 compile() 时注入的——graph 本身不知道、也不关心 checkpoint 存在哪。所以从内存换到 Postgres，图的定义代码一行不改。这是面试常考的设计题答案。

概念 ②: thread_id —— 会话的钥匙

checkpointer 内部按 thread_id 分格子存快照（源码里就是一个 defaultdict(thread_id → checkpoints)）。所以你要告诉它：这次调用属于哪个会话。方式是给 invoke() 传第二个参数 config：

config = {"configurable": {"thread_id": "thread-1"}}
graph.invoke({"messages": [HumanMessage(content="...")]}, config)

⚠️ Gotcha：thread_id 必须嵌在 "configurable" 里，不能放顶层。这个双层 dict 没人能猜出来，只能记住。为什么这么设计？invoke() 的第二个参数是通用的 RunnableConfig（LangChain 全家共用的运行配置，还能放 callbacks、max_concurrency 等），"configurable" 是它留给「运行时可变参数」的抽屉，thread_id 只是抽屉里的一件。挂了 checkpointer 却不传 thread_id 会直接报错——我实测的原文：

ValueError: Checkpointer requires one or more of the following
'configurable' keys: thread_id, checkpoint_ns, checkpoint_id

于是多轮对话变成这样，注意第二轮只传了一条新消息：

# 第 1 轮：auth-service 有多少违规？     → 消息数 4（问 + tool_call + 结果 + 回答）
graph.invoke({"messages": [HumanMessage(content=q1)]}, config)

# 第 2 轮：那它的可信分数呢？            → 消息数 8，历史在累积
graph.invoke({"messages": [HumanMessage(content=q2)]}, config)   # ← 没传任何历史！

历史不在你的输入里——在 checkpoint 里。LangGraph 拿 thread_id 取回第 1 轮结束时的 State，用 reducer 把 q2 合并进去，LLM 看到的 messages 自动是完整 8 条。换一个 thread_id，同一个 graph 对象立刻"失忆"：记忆按 thread_id 隔离，多用户/多会话天然互不串线。这个模型对照你的后端经验很好理解：thread_id ≈ 会话 ID，checkpointer ≈ 会话存储，只是存的是 State 快照而不是 session blob。

概念 ③: get_state() —— 亲眼看见 checkpoint

记忆不能是个黑盒。任何时候都能查一个 thread 的现状：

snapshot = graph.get_state(config)

snapshot.values          # 当前完整 State，.values["messages"] 就是那 8 条消息
snapshot.next            # 下一个待执行的节点；() 空元组 = 图跑完了，在等下一轮输入
snapshot.config["configurable"]
                         # {'thread_id': 'thread-1', 'checkpoint_id': '1f19be4e-...'}
                         #            ↑ invoke 之后被自动追加，指向最新快照

list(graph.get_state_history(config))   # 每个超步一份快照（上面两轮共 10 份）
                                         # —— time travel / 回放 / 分叉的原料，下下课细讲

记住三件套：.values（现在什么样）、.next（接下来谁执行）、history（一路怎么来的）。调试 Agent 时 get_state 就是你的 print——不用在 node 里到处插日志。

卡住了？点开看三处空白的答案

15_memory_saver.py 完整答案 
# ① compile 时注入 checkpointer
graph = graph_builder.compile(checkpointer=checkpointer)

# ② thread_id 必须嵌在 "configurable" 里 —— 双层 dict，记住它
config = {"configurable": {"thread_id": "thread-1"}}

# ③ 只传新问题这一条消息，历史由 checkpoint 自动带回
result = graph.invoke({"messages": [HumanMessage(content=q2)]}, config)

改造任务的骨架：while True: q = input("🧑 "); if q == "exit": break; graph.invoke({"messages": [HumanMessage(content=q)]}, config)——注意循环里从头到尾不需要任何 messages 变量。

本课一句话总结

compile(checkpointer=...) 让每个超步后的 State 自动存档；{"configurable": {"thread_id": ...}} 是会话的钥匙——同 key 取回历史，新 key 空白开局；get_state() 让记忆不再是黑盒。记忆不是模型的超能力，是工程上的存取问题——而你早就会做会话存储了。
