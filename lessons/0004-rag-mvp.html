Lesson 0004 · Week 1 收官

可信文档问答 MVP：封装、门控、引用

把 RAG 打包成可复用模块 + 相似度门控（不瞎编）+ 来源引用（可追溯）

⏱️ 约 45 分钟 动手课 📅 Week 1 · Day 4

Lesson 3 留下的三个缺口

Lesson 3 的 07_rag_chromadb.py 能跑通 RAG 了，但作为"可信文档问答 MVP"还差三件事：

  1. 不可复用。建索引、检索、生成混在一个脚本里。换个问题要改 query 变量重跑；别的程序想调用它也调不了。
  2. 不可交互。没有问答界面，每次都得改代码。
  3. 最致命 —— 它会瞎编。问它"今天天气怎么样"，它照样会从那 4 段可信规范里挑一段最不挨边的，编出一套"天气相关的可信构建建议"。对"可信"系统来说，一本正经地胡说八道比答不出来严重得多。

一个可信的问答系统必须做到两件事：

  • 知道自己不知道 —— 文档里没有就明说，不编（这叫防幻觉 / anti-hallucination）
  • 说清答案哪来的 —— 附上引用来源，让人能验证（这叫可追溯 / traceability）
🎯 这正是"可信看板"的灵魂

可信看板的核心价值就是可追溯 —— 每个工程结论都要能追溯到具体规范。如果 AI 助手给出"建议重构这个模块"，用户必须能点开看到"因为规范第 X 条 + 这段扫描数据"。这节课把"门控 + 引用"做进去，就是给你的 MVP 注入"可信"基因。

知识 ①：从脚本到模块（封装）

把 Lesson 3 的过程式脚本重构成一个类，核心是关注点分离（separation of concerns）：

方法 职责 调用频率
index_documents(text) 切分 + 向量化 + 存入 ChromaDB 文档变更时调一次
retrieve(query) 检索 top-k 相关 chunk 每次提问
ask(query) 检索 + 门控 + 生成 每次提问（对外接口）

对外只暴露 ask(question) 一行接口。建索引是"一次性投入"，问答是"反复使用"——把它们分开，索引建一次就能问无数次。

💡 文件命名的小升级

前几课的文件是 01_chat.py、07_rag_chromadb.py —— 带编号的独立脚本。这课开始我们写可导入的模块 rag.py（被别人 import），所以不带编号、用语义化命名（编号开头也不能做模块名，Python 不允许数字开头的标识符）。从"一次性脚本"毕业到"可复用模块"，这本身就是工程化的里程碑。

知识 ②：相似度门控（防幻觉的第一道防线）

问题在哪？retrieve() 永远会返回 top-k 个 chunk —— 哪怕最相关的那个其实也跟问题八竿子打不着。向量数据库只负责"相对最像"，不负责"到底像不像"。

解法：设一个相似度阈值（threshold）。把 ChromaDB 返回的 distance 换算回 cosine similarity（sim = 1 - distance），如果最相关那条的相似度都低于阈值，就判定"文档里没有相关信息"，直接拒答，不调用 LLM。

用户提问 → retrieve top-k → 最相关 chunk 的相似度够高吗？
                              │
                    ┌─────────┴─────────┐
                   够高                不够高（< 阈值）
                    │                    │
            拼上下文 → LLM 生成      直接答"文档里没有相关信息"
            （附引用来源）            （不瞎编，省 token，省时间）

图 1：相似度门控 —— 在调用 LLM 之前就拦住"没答案"的问题

⚠️ 阈值是经验值，要调

SIM_THRESHOLD = 0.5 只是个起点。不同 embedding 模型、不同语料，相似度分布不同。本课会把每次检索的相似度打印出来，你观察一下：相关问题通常 0.6–0.85，无关问题通常 0.2–0.4。根据你的真实数据调整阈值。这是 RAG 工程里最常调的参数之一。

知识 ③：来源引用（可追溯）

门控解决了"不瞎编"，引用解决"可验证"。ask() 除了返回答案，还返回这次用了哪些 chunk、各自相似度多少。展示给用户，用户就能：点开原文核对 → 判断 AI 说的靠不靠谱。

对可信看板：以后每条 AI 建议都能附上"基于规范 chunk-3（相似度 0.81）"，这就是"可信"的工程化落地。

Task ①：把 RAG 封装成 rag.py 模块

1 动手：写 TrustRAG 类

目标：把 Lesson 3 的流程封装成 rag.py，对外暴露 index_documents() 和 ask()。

  1. 创建文件 src/teach_ai/rag.py，写入以下代码：

    import chromadb
from openai import OpenAI
from teach_ai.envs import GLM_KEY, DS_KEY

EMBED_MODEL = "embedding-3"
CHAT_MODEL = "deepseek-v4-flash"
SIM_THRESHOLD = 0.5   # 低于这个相似度视为"文档里没有" —— 运行后根据观察调整


class TrustRAG:
    """可信文档问答：建索引一次，问答多次。"""

    def __init__(self, db_path="./chroma_db", collection="trust_docs"):
        self.zhipu = OpenAI(api_key=GLM_KEY, base_url="https://open.bigmodel.cn/api/paas/v4/")
        self.deepseek = OpenAI(api_key=DS_KEY, base_url="https://api.deepseek.com")
        self.client = chromadb.PersistentClient(path=db_path)
        self.collection = self.client.get_or_create_collection(
            name=collection,
            configuration={"hnsw": {"space": "cosine"}},
        )

    @staticmethod
    def _split(text):
        """按段落切分（复用 Lesson 3 的切分器）。"""
        return [p.strip() for p in text.split("\n\n") if p.strip()]

    def _embed(self, texts):
        """用智谱把文本列表转成向量列表。"""
        resp = self.zhipu.embeddings.create(model=EMBED_MODEL, input=texts)
        return [item.embedding for item in resp.data]

    def index_documents(self, text):
        """切分 → 向量化 → 存入 ChromaDB。建索引，文档变更时调一次即可。"""
        chunks = self._split(text)
        vectors = self._embed(chunks)
        self.collection.upsert(
            ids=[f"chunk-{i}" for i in range(len(chunks))],
            documents=chunks,
            embeddings=vectors,
            metadatas=[{"index": i} for i in range(len(chunks))],
        )
        return len(chunks)

    def retrieve(self, query, k=3):
        """检索 top-k 相关 chunk，返回 (chunks, similarities)。"""
        query_vec = self._embed([query])[0]
        results = self.collection.query(query_embeddings=[query_vec], n_results=k)
        chunks = results["documents"][0]
        # cosine distance → cosine similarity（越大越相似）
        sims = [1 - dist for dist in results["distances"][0]]
        return chunks, sims

    def ask(self, query, k=3):
        """问答 = 检索 + 门控 + 生成。返回 (answer, similarities)。"""
        chunks, sims = self.retrieve(query, k=k)

        # ── 门控：最相关 chunk 的相似度太低 → 文档里没有，不瞎编 ──
        # sims 已按相似度从高到低排好，sims[0] 就是最相关的那条
        if not chunks or sims[0] < SIM_THRESHOLD:
            return "抱歉，文档里没有与该问题相关的信息。", sims

        # ── 通过门控：拼接上下文，调用 DeepSeek 生成 ──
        context = "\n\n".join(chunks)
        chat = self.deepseek.chat.completions.create(
            model=CHAT_MODEL,
            messages=[
                {
                    "role": "system",
                    "content": "你是可信工程助手。仅基于参考文档回答，不要编造。"
                               "文档中没有的信息请明确说明。",
                },
                {"role": "user", "content": f"参考文档:\n{context}\n\n问题: {query}"},
            ],
            temperature=0.2,
            max_tokens=400,
        )
        return chat.choices[0].message.content, sims
✅ 检查点

这个文件没有顶层的执行代码（没有 if __name__），所以直接运行它不会有输出 —— 它是一个被导入的模块。下一 Task 写的程序会 import 它。先确认 python -c "from teach_ai.rag import TrustRAG; print('OK')"（在项目根目录用 uv run 跑）能打印 OK，说明模块无误。

设计要点回顾

  • _split / _embed 用下划线开头 —— 约定俗成的"内部方法"，外部不该直接调
  • retrieve() 把 distance 换算成 similarity 返回，让门控和引用都用"越大越相似"的直觉（和 Lesson 2 一致）
  • ask() 是唯一对外的问答接口，门控逻辑藏在里面，调用方不用关心

Task ②：写交互式问答 qa.py

2 动手：命令行问答界面

目标：写一个能持续提问的 CLI，把答案和相似度引用都打印出来。

  1. 创建文件 src/teach_ai/qa.py，写入以下代码：

    from teach_ai.rag import TrustRAG

# 样例文档（和 Lesson 3 同一份）。真实项目里从文件加载 —— 下节会讲
TRUST_DOCS = """编码规范检查是可信工程的第一道防线。团队通过 ESLint、Pylint、SonarQube 等静态分析工具自动扫描源代码，识别不符合规范的命名、格式、复杂度等问题。检查结果同步到可信看板，按组件维度聚合，指导开发者逐项修复。

可信构建要求在可控、可追溯的环境中执行软件构建。每次构建的源码版本、依赖清单、构建参数都必须完整记录，确保产物与源码的对应关系可验证。这是防范供应链攻击、保证产物完整性的关键环节。

代码度量通过圈复杂度、代码行数、重复率、注释率等量化指标评估代码质量。可信看板将这些指标按模块可视化，帮助团队识别高风险、需重构的模块。通常圈复杂度超过 15 的函数会被标记为需要关注。

组件化是将复杂系统拆分为高内聚、低耦合的独立组件，每个组件有清晰的接口契约和版本管理。可信看板跟踪各组件的接口稳定性、依赖关系和变更频率，以此评估组件化成熟度。"""


def main():
    rag = TrustRAG()
    n = rag.index_documents(TRUST_DOCS)   # 已索引则 upsert 覆盖，幂等
    print(f"已索引 {n} 个 chunk 到可信文档库")

    print("\n可信文档问答 MVP（输入 quit 退出）")
    print("=" * 40)

    while True:
        query = input("\n你的问题> ").strip()
        if query.lower() in ("quit", "exit", "q"):
            print("再见！")
            break
        if not query:
            continue

        answer, sims = rag.ask(query)
        print(f"\n答: {answer}")
        scores = ", ".join(f"{s:.2f}" for s in sims)
        print(f"📚 top-{len(sims)} 相似度: [{scores}]  (阈值 0.50)")


if __name__ == "__main__":
    main()

  2. 在项目根目录运行（注意是 uv run，这样 teach_ai 包能被导入）：

    uv run python src/teach_ai/qa.py

Task ③：亲手验证"门控"和"引用"

3 动手：问三类问题，观察相似度

目标：用真实提问感受阈值的作用，理解"可信"是如何被工程化的。

依次输入下面三个问题，重点看每条回答下面的相似度：

  1. 相关问题（应该在库里）：

    代码圈复杂度超过多少需要关注？

    预期：top-1 相似度 0.6 以上，DeepSeek 给出基于文档的回答（提到 15）。

  2. 擦边问题（主题相关但库里没有细节）：

    可信构建具体用的是什么构建工具？

    预期：相似度中等。看它是否会"老实说文档里没提工具名"——这考验 system prompt + 模型的诚实度。

  3. 完全无关的问题（库外）：

    怎么做红烧肉？

    预期：top-1 相似度跌到 0.4 以下（低于阈值 0.5），系统直接拒答，根本不调用 LLM。这就是门控在工作。

✅ 检查点：你应该体会到的

第三题被拦在 LLM 之前 —— 它不会用红烧肉的问题去编造一段"可信构建红烧肉指南"。这就是 Lesson 3 那个会瞎编的脚本和现在这个 MVP 的本质区别。如果某题明明相关却被拒答，把 SIM_THRESHOLD 调低（比如 0.4）再试；如果无关题没被拦住，调高（比如 0.55）。这就是调阈值的过程。

💡 门控只是防幻觉的起点

相似度阈值拦得住"完全不相关"的问题，但拦不住"检索到看似相关、实则不对的 chunk，然后 LLM 据此发挥"的情况。生产级 RAG 还会用 reranking（重排）、LLM-as-judge（让另一个 LLM 判断答案是否真的有依据）、引用精确匹配等手段。这些在 Week 2–4 会逐步引入。现在先掌握最基础也最有效的一道防线。

Week 2 预告：LangChain / LCEL

Week 1 你手写了 RAG 的每一步。Week 2 我们引入 LangChain / LCEL，用框架把这套流程重写得更简洁、更可组合：

  • Prompt Template：把 system/user 模板化，告别 f-string 手拼
  • LCEL 管道：retriever | prompt | llm | parser 一行串起整个 RAG
  • Document Loaders + RecursiveCharacterTextSplitter：从真实文件加载、智能切分
  • Tool Calling：让 LLM 主动调用工具（可信看板数据分析的入口）

你会清楚看到：框架没有做魔法，它只是把你 Week 1 手写的步骤封装成了可组合的积木。因为你手写过，所以你能看穿框架、定位问题、做技术选型——这正是面试官想听到的的那种理解深度。
