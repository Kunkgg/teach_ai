Lesson 0008

让 LLM 调用你的 Python 函数

Tool Calling / Function Calling

⏱️ 约 25–35 分钟 动手课 📅 Week 2

从 RAG 到 Agent 的跳板

经过 7 节课，RAG pipeline 六步已全部打通——LLM 能阅读你的文档了。但如果你想让它：

  • 查询数据库里某个组件的实时违规数？
  • 调用 API 触发一次可信构建扫描？
  • 计算两个版本之间的可信分数变化？

LLM 只会生成文本，它做不了这些事。Tool Calling（工具调用）解决的就是这个问题——让 LLM 能"调用"你写的 Python 函数。

知识 ①：核心心智模型 — LLM 不执行代码

Tool Calling 最容易搞混的一点：LLM 自己并不执行函数。它只做一件事——生成一段 JSON，告诉你"请调用这个函数，参数是这些"。

你的问题: "auth-service 有多少条违规？"
    │
    ▼  Step 1: 发给 LLM（附带工具清单）
┌───────────────────────────────────────────┐
│ LLM 思考：这个问题需要查数据，我手头有    │
│ count_violations 工具，参数要 component    │
│                                           │
│ → 返回 JSON:                              │
│   name: "count_violations"                │
│   args: {"component": "auth-service"}     │
│   id:   "call_abc123"                     │
└───────────────────────────────────────────┘
    │
    ▼  Step 2: 你的代码执行函数
    result = count_violations("auth-service")  → 12
    │
    ▼  Step 3: 把结果包装成 ToolMessage 发回 LLM
    │
    ▼  Step 4: LLM 用自然语言回答
    "auth-service 目前有 12 条编码规范违规。"

图 1：Tool Calling 四步循环——LLM 只产出 JSON，你的代码负责执行

⚠️ 面试高频考点

"LLM 真的执行了函数吗？" 答案：没有。LLM 只产出一段 JSON（函数名 + 参数），告诉你的代码该调用什么。执行是你的代码做的。这个区分是理解 Agent 架构的基础。

知识 ②：@tool + bind_tools + tool_calls

在 LangChain 中，Tool Calling 有 4 个步骤：

Step 1：用 @tool 定义工具

from langchain_core.tools import tool

@tool
def count_violations(component: str) -> int:
    """查询指定组件的编码规范违规数量。"""
    return db.query(component)  # 你的业务逻辑

@tool 装饰器干了什么？它把函数的 docstring（描述）和 类型注解（参数类型）转换成一份 JSON Schema，LLM 靠这份 Schema 知道"有这个工具可用、它做什么、需要什么参数"。所以 docstring 写得好不好，直接影响 LLM 是否能正确选择工具。

Step 2：用 bind_tools 把工具交给模型

llm_with_tools = llm.bind_tools([count_violations, get_trust_score])

bind_tools() 返回一个新的 Runnable，每次调用时都会把工具的 JSON Schema 注入 API 请求。

Step 3：模型返回 AIMessage.tool_calls

ai_msg = llm_with_tools.invoke(messages)
print(ai_msg.tool_calls)
# [{"name": "count_violations", "args": {"component": "auth-service"}, "id": "call_abc123"}]

.tool_calls 是一个列表——因为 LLM 可能一次请求调用多个工具（并行调用）。每个条目有三个字段：name（函数名）、args（参数字典）、id（唯一请求 ID）。

Step 4：执行工具，用 ToolMessage 返回结果

result = selected_tool.invoke(tool_call)
tool_msg = ToolMessage(content=str(result), tool_call_id=tool_call["id"])

tool_call_id 必须和 AIMessage 里的 id 一一对应——API 协议要求这样。LLM 靠 ID 把执行结果对应回具体的调用请求。

💡 对照 Week 1

Week 1 如果你要根据用户问题调用不同函数，得写 if "违规" in question: count_violations(...) 这样的硬编码分支。Tool Calling 把"选哪个函数、提取什么参数"这件事交给了 LLM——它比 if/elif 灵活得多，因为它理解自然语言。

知识 ③：对照表 — 手写分支 vs Tool Calling

12_tool_calling.py 三处空白的答案 
# ① 只需一个装饰器
@tool
def count_violations(component: str) -> int:

# ② bind_tools 接收工具列表
llm_with_tools = llm.bind_tools(tools)

# ③ 构造 ToolMessage，content 必须是字符串，tool_call_id 必须匹配
tool_msg = ToolMessage(content=str(result), tool_call_id=tc["id"])

为什么 content 要用 str(result)？ 因为 ToolMessage.content 必须是字符串（它会被发送给 LLM 作为文本输入），而 count_violations 返回的是 int。

为什么 tool_call_id 要取 tc["id"]？ 因为 API 要求每个 ToolMessage 的 ID 和它响应的那个 tool_call 的 ID 一一对应。如果 LLM 一次请求了两个工具调用，它需要靠 ID 区分哪个结果属于哪个请求。

连接 Agent：while 循环 = Agent

如果你把刚才的 4 步（调用模型 → 检查 tool_calls → 执行工具 → 返回结果）放进一个 while 循环，直到 LLM 不再返回 tool_calls 为止……

while True:
    ai_msg = llm_with_tools.invoke(messages)
    if not ai_msg.tool_calls:
        break           # LLM 认为不需要更多工具了，循环结束
    # 执行工具、构造 ToolMessage、append 到 messages...

print(ai_msg.content)   # 最终的自然语言回答
