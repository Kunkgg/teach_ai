Lesson 0003

向量数据库与文档切分

从 Python list 升级到 ChromaDB — 持久化、高效检索、能查真实文档

⏱️ 约 40 分钟 动手课 📅 Week 1 · Day 3

上一课留下了两个问题

在 Lesson 0002 里，你用 3 段文档搭了一个 Mini RAG：把向量存在一个 Python list 里，遍历计算余弦相似度，取最高的那段交给 DeepSeek。它能跑通，但有两个硬伤：

  1. 慢且不可扩展。每查一次，都要和 所有 向量逐个比对（O(n)）。如果你有 1000 篇文档、每篇切成 20 个 chunk，就是 20000 个向量 —— 每次查询都要算 20000 次相似度。
  2. 数据不持久。程序一退出，Python list 里的向量就没了。下次运行还得重新 embedding、重新存 —— 浪费 API 调用，也浪费钱。

这节课解决这两个问题。你需要两样新东西：

  • 向量数据库（ChromaDB） —— 高效检索 + 持久化存储
  • 文档切分（Chunking） —— 把一篇长文档切成可被精准检索的小块
🎯 和可信看板的关系

可信看板有大量可信规范文档（编码规范、度量标准、构建流程……）。你要让用户用自然语言查询这些文档。这节课结束时，你会有一个能持久化存储真实文档、按语义检索、基于文档回答的 RAG pipeline —— 这就是"可信文档问答 MVP"的雏形。

知识 ①：为什么需要向量数据库？

Lesson 2 的做法叫暴力搜索（brute-force / flat search）：查询向量和库里每个向量都算一次相似度，再排序。文档少时没问题，文档一多就扛不住。

向量数据库用一种叫 ANN（Approximate Nearest Neighbor，近似最近邻）的索引结构（ChromaDB 用的是 HNSW），把"找最相似的 K 个向量"从近似 O(n) 降到接近 O(log n)。代价是结果近似（不保证 100% 是全局最优），但在 RAG 场景里这点误差完全可以接受 —— 换来的是几个数量级的速度提升。

除了快，向量数据库还提供：

  • 持久化：向量写到磁盘，程序重启不丢
  • 元数据过滤：可以按 source、date 等字段先筛选再检索
  • 增删改查：文档更新时可以 upsert / delete
Mini RAG (Lesson 2)              ChromaDB RAG (本课)
─────────────────────            ─────────────────────────
query → embed                    query → embed
       ↓                                ↓
  遍历 list 逐个比对         ChromaDB 用 ANN 索引高效召回 top-k  ← 快
       ↓                                ↓
  手动 sort 取最高              结果已按相似度排好（无需手动 sort）
       ↓                                ↓
  程序退出 → 数据丢失           数据持久化在磁盘  ← 不丢

图 1：从"手动遍历"到"向量数据库检索"

知识 ②：Chunking — 把文档切成块

为什么要切？

你不能把整篇长文档当成一个向量。原因有二：

  1. 检索精度。如果一整个 chunk 混杂了"编码规范 + 度量 + 构建"三个主题，它的向量是三个主题的"平均值"，查询任何一个主题都匹配得不精准。切成主题单一的小块，检索才准。
  2. Context window 限制。检索出来的内容要塞进 prompt 给 LLM。小块更省 token，也更聚焦。

切多大？这是 RAG 最重要的调参点之一

策略 效果
太大 一个 chunk 混杂多主题 → 检索不精准；塞进 prompt 浪费 token
太小 语义不完整 → LLM 拿到的上下文碎片化，无法理解
合适 每个 chunk 表达一个完整的小概念 —— 这是目标

常见的切分策略

  • 按结构切：按段落（空行）、按标题、按 Markdown 章节。最自然，保留语义边界。本课用这种。
  • 按固定大小 + overlap：每 N 个字符切一刀，相邻块之间重叠 M 个字符，避免在关键词中间切断。
  • 递归切分（Recursive）：先按段落切，段落太长再按句子，句子太长再按字符。LangChain 的 RecursiveCharacterTextSplitter 就是这个 —— Week 2 会用到。
💡 Overlap（重叠）是什么？

固定大小切分时，如果一个关键句正好被切在两个 chunk 的边界上，它就被劈成两半，两边都搜不全。Overlap 让相邻 chunk 共享一小段文本（比如重叠 50 字符），边界处的信息在两个 chunk 里都出现，降低"切坏"的概率。

知识 ③：ChromaDB 心智模型

把 ChromaDB 想成一个数据库，它有三层结构：

概念 类比 说明
Client 数据库连接 入口。PersistentClient(path=...) 把数据存到磁盘；Client() 只存内存（测试用）
Collection 一张表 存放一类向量。get_or_create_collection(name=...) 获取或创建
一条记录 一行数据 由 id + document(原文) + embedding(向量) + metadata(元数据) 组成

四个核心操作：

方法 作用
collection.add(...) 新增记录（id 重复会报错）
collection.upsert(...) 新增或更新（id 存在则覆盖）—— 重复运行脚本时用它，避免重复数据
collection.query(...) 语义检索，返回最相似的 top-k 条
collection.get(...) 按 id 或元数据精确取记录
⚠️ query 返回的是嵌套结构

query() 可以同时查多个问题，所以返回值是嵌套列表：results["documents"][0] 才是第一个查询召回的文档列表。漏写 [0] 是最常见的初学者错误。

环境准备：API key 从代码里搬到 .env

Lesson 2 里你把 API key 直接写进了代码（"你的-DeepSeek-API-Key"）。这在练习时方便，但有隐患：key 一旦提交到 git 就泄露了。把密钥放进环境变量是工程师的基本功，从这节课开始我们正式这么做。

你的项目里已经有 envs.py 在做这件事。回顾一下它的逻辑：

# .env 文件（不要提交到 git！确认它在 .gitignore 里）
DS_KEY=sk-你的-deepseek-key
GLM_KEY=你的-智谱-key
# src/teach_ai/envs.py —— 你的项目里已有这个文件
import os
from dotenv import load_dotenv

load_dotenv()                  # 把 .env 的内容加载进环境变量
DS_KEY = os.getenv("DS_KEY")   # DeepSeek（Chat）
GLM_KEY = os.getenv("GLM_KEY") # 智谱（Embedding）

本课所有脚本都用 from teach_ai.envs import GLM_KEY, DS_KEY 来取 key。如果你还没建 envs.py，照上面抄一份即可。

💡 为什么这样设计？

代码和环境配置分离 —— 同一份代码，换一台机器只需改 .env，不用动代码。这也是 LangChain 等框架读取配置的标准方式，先习惯起来。

Task ①：ChromaDB 基础操作

1 动手：建库、存向量、查向量

目标：用 ChromaDB 存 3 条带向量的记录，做一次检索，看清返回结构。

  1. 安装 ChromaDB（你用的是 uv）：

    uv add chromadb

# 如果你不用 uv，等价命令：
# pip install chromadb

  2. 创建文件 05_chromadb_basics.py，写入以下代码：

    import chromadb
from openai import OpenAI
from teach_ai.envs import GLM_KEY

# 智谱客户端（做 Embedding）
zhipu = OpenAI(api_key=GLM_KEY, base_url="https://open.bigmodel.cn/api/paas/v4/")

# ── Step 1: 建一个持久化客户端 + 集合 ──
# 数据会写到 ./chroma_db 文件夹，程序重启后还在
client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_or_create_collection(
    name="trust_basics",
    metadata={"hnsw:space": "cosine"},   # 用 cosine 距离，和 Lesson 2 一致
)

# ── Step 2: 准备 3 段文本，用智谱转成向量 ──
texts = [
    "编码规范检查用静态分析工具扫描源代码，发现命名、格式等问题。",
    "可信构建在可追溯的环境中执行构建，防止供应链攻击。",
    "代码度量用圈复杂度、重复率等指标量化评估代码质量。",
]
emb_resp = zhipu.embeddings.create(model="embedding-3", input=texts)
vectors = [item.embedding for item in emb_resp.data]

# ── Step 3: 存入 ChromaDB（注意我们手动传了 embeddings）──
collection.upsert(
    ids=["b1", "b2", "b3"],
    documents=texts,
    embeddings=vectors,
    metadatas=[{"topic": t[:4]} for t in ["编码规范", "可信构建", "代码度量"]],
)
print(f"集合里有 {collection.count()} 条记录")

# ── Step 4: 提一个问题，检索最相似的 2 条 ──
query = "怎么衡量代码质量？"
query_vec = zhipu.embeddings.create(model="embedding-3", input=[query]).data[0].embedding

results = collection.query(query_embeddings=[query_vec], n_results=2)

# results["documents"] 是嵌套列表 —— [0] 取第一个查询的结果
print("\n最相关的 2 条:")
for doc, dist in zip(results["documents"][0], results["distances"][0]):
    print(f"  [距离 {dist:.4f}] {doc}")

  3. 运行它：

    python 05_chromadb_basics.py
✅ 检查点：你应该看到

"代码度量"那条的距离最小（最相似）。再运行一次脚本 —— 输出不变，而且不会报"id 重复"错（因为用了 upsert）。检查项目目录，多了一个 chroma_db/ 文件夹 —— 那就是持久化的数据。

代码解析：我们手动传了 embeddings

注意 Step 3 里我们同时传了 documents 和 embeddings。ChromaDB 默认会用它自带的 embedding 模型（需要联网下载），但因为我们自己用智谱算好了向量并传进去，ChromaDB 就直接用我们的向量，不会去下载任何模型。这也保证了存进去的向量和 Lesson 2 你手算的是同一套（智谱 embedding-3）。

💡 distances 和"相似度"的关系

ChromaDB 返回的是 distance（距离），越小越相似 —— 这和 Lesson 2 的余弦相似度（越大越相似）正好相反。我们配了 cosine 空间，所以这里的 distance ≈ 1 - 余弦相似度。结果已经按相似度从高到低排好，documents[0] 就是最佳匹配 —— 你不用再像 Lesson 2 那样手动 sort 了。

Task ②：把文档切分成 chunks

2 动手：Chunking

目标：把一份多段落的可信规范文档，按段落切成可检索的 chunk，观察结果。

  1. 创建文件 06_chunking.py，写入以下代码：

    # 一份（简化版）可信编码规范文档 —— 4 个主题段落，用空行分隔
TRUST_DOCS = """编码规范检查是可信工程的第一道防线。团队通过 ESLint、Pylint、SonarQube 等静态分析工具自动扫描源代码，识别不符合规范的命名、格式、复杂度等问题。检查结果同步到可信看板，按组件维度聚合，指导开发者逐项修复。

可信构建要求在可控、可追溯的环境中执行软件构建。每次构建的源码版本、依赖清单、构建参数都必须完整记录，确保产物与源码的对应关系可验证。这是防范供应链攻击、保证产物完整性的关键环节。

代码度量通过圈复杂度、代码行数、重复率、注释率等量化指标评估代码质量。可信看板将这些指标按模块可视化，帮助团队识别高风险、需重构的模块。通常圈复杂度超过 15 的函数会被标记为需要关注。

组件化是将复杂系统拆分为高内聚、低耦合的独立组件，每个组件有清晰的接口契约和版本管理。可信看板跟踪各组件的接口稳定性、依赖关系和变更频率，以此评估组件化成熟度。"""


def split_by_paragraph(text):
    """按空行（段落）切分，丢弃空白段落。最自然的切分方式。"""
    return [p.strip() for p in text.split("\n\n") if p.strip()]


chunks = split_by_paragraph(TRUST_DOCS)

print(f"文档总长 {len(TRUST_DOCS)} 字符，切成 {len(chunks)} 个 chunk:\n")
for i, chunk in enumerate(chunks):
    print(f"── chunk {i} ({len(chunk)} 字符) ──")
    print(chunk)
    print()

  2. 运行它：

    python 06_chunking.py
✅ 检查点：你应该看到

4 个 chunk，每个大约 80–110 字符，且每个都只讲一个主题（编码规范 / 可信构建 / 代码度量 / 组件化）。这就是好的 chunk —— 主题单一、语义完整。

📖 进阶：固定大小 + overlap

按段落切很自然，但遇到一个超长段落（没有空行）就会得到一个巨大的 chunk。生产环境更常用的是递归切分：先按段落，段落太长就按句子，再不行按字符，并加上 overlap。LangChain 的 RecursiveCharacterTextSplitter 就是干这个的 —— Week 2 我们会正式介绍。现在先理解"为什么要切"，工具后面有。

Task ③：端到端 RAG with ChromaDB

3 动手：完整 RAG pipeline（加载 → 切分 → 向量化 → 存储 → 检索 → 生成）

目标：把 Task ② 的文档灌进 ChromaDB，提问 → 检索 top-k → DeepSeek 基于文档回答。这是 Week 1 MVP 的核心。

  1. 创建文件 07_rag_chromadb.py，写入以下代码：

    import chromadb
from openai import OpenAI
from teach_ai.envs import GLM_KEY, DS_KEY

# 两个客户端：智谱做 Embedding，DeepSeek 做 Chat
zhipu = OpenAI(api_key=GLM_KEY, base_url="https://open.bigmodel.cn/api/paas/v4/")
deepseek = OpenAI(api_key=DS_KEY, base_url="https://api.deepseek.com")

# ── Step 1: 文档 + 切分（复用 Task ② 的切分器）──
TRUST_DOCS = """编码规范检查是可信工程的第一道防线。团队通过 ESLint、Pylint、SonarQube 等静态分析工具自动扫描源代码，识别不符合规范的命名、格式、复杂度等问题。检查结果同步到可信看板，按组件维度聚合，指导开发者逐项修复。

可信构建要求在可控、可追溯的环境中执行软件构建。每次构建的源码版本、依赖清单、构建参数都必须完整记录，确保产物与源码的对应关系可验证。这是防范供应链攻击、保证产物完整性的关键环节。

代码度量通过圈复杂度、代码行数、重复率、注释率等量化指标评估代码质量。可信看板将这些指标按模块可视化，帮助团队识别高风险、需重构的模块。通常圈复杂度超过 15 的函数会被标记为需要关注。

组件化是将复杂系统拆分为高内聚、低耦合的独立组件，每个组件有清晰的接口契约和版本管理。可信看板跟踪各组件的接口稳定性、依赖关系和变更频率，以此评估组件化成熟度。"""


def split_by_paragraph(text):
    return [p.strip() for p in text.split("\n\n") if p.strip()]


chunks = split_by_paragraph(TRUST_DOCS)

# ── Step 2: 用智谱把每个 chunk 向量化 ──
emb_resp = zhipu.embeddings.create(model="embedding-3", input=chunks)
chunk_vectors = [item.embedding for item in emb_resp.data]

# ── Step 3: 存入 ChromaDB（持久化）──
client = chromadb.PersistentClient(path="./chroma_db")
collection = client.get_or_create_collection(
    name="trust_docs",
    metadata={"hnsw:space": "cosine"},
)
collection.upsert(
    ids=[f"chunk-{i}" for i in range(len(chunks))],
    documents=chunks,
    embeddings=chunk_vectors,
    metadatas=[{"source": "可信编码规范", "index": i} for i in range(len(chunks))],
)
print(f"已存入 {collection.count()} 条 chunk 到 ChromaDB")

# ── Step 4: 提问 → 向量化 → 检索 top-k ──
query = "代码圈复杂度超过多少需要关注？"
query_vec = zhipu.embeddings.create(model="embedding-3", input=[query]).data[0].embedding

results = collection.query(query_embeddings=[query_vec], n_results=2)
top_chunks = results["documents"][0]   # 嵌套结构，[0] 取第一个查询的结果

print(f"\n检索到 {len(top_chunks)} 条相关片段:")
for i, doc in enumerate(top_chunks):
    print(f"  [{i + 1}] {doc[:40]}...")

# ── Step 5: 拼接上下文 → DeepSeek 生成回答 ──
context = "\n\n".join(top_chunks)
chat = deepseek.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[
        {
            "role": "system",
            "content": "你是可信工程助手。仅基于参考文档回答，不要编造。"
                       "文档中没有的信息请明确说明。",
        },
        {"role": "user", "content": f"参考文档:\n{context}\n\n问题: {query}"},
    ],
    temperature=0.2,
    max_tokens=300,
)

print("\n" + "─" * 50)
print(f"问题: {query}")
print(f"回答: {chat.choices[0].message.content}")

  2. 运行它：

    python 07_rag_chromadb.py

  3. 验证持久化：把 Step 2–3（向量化 + 存入）整段注释掉，只保留提问和检索部分，再运行一次。你会发现照样能检索到结果 —— 因为数据已经在 chroma_db/ 里了。这就是向量数据库持久化的价值。

✅ 检查点

检索召回的应该是"代码度量"那段（含"圈复杂度超过 15"）。DeepSeek 的回答应该明确提到 15 这个数字 —— 因为它来自检索到的文档，而不是模型自己编的。试试改 query 问"什么是可信构建"、"组件化成熟度怎么评估"，验证它每次都能定位到正确的段落。

💡 对比 Lesson 2 的 Mini RAG

流程几乎一样（embed → 找最相关 → 喂给 LLM），但变了三件事：① 文档先切分成 chunk；② 向量存进 ChromaDB 而不是 Python list；③ 检索 top-k（多条）而不是只取 1 条，给 LLM 更完整的上下文。这就是从"玩具"到"可用"的跨越。

今天学到了什么

  1. 向量数据库用 ANN 索引把检索从 O(n) 降到接近 O(log n)，还提供持久化和元数据过滤 —— ChromaDB 是轻量本地首选
  2. Chunking 把长文档切成主题单一的小块，是 RAG 检索质量的命脉：太大不精准，太小丢上下文
  3. ChromaDB 心智模型：Client → Collection → 记录（id + document + embedding + metadata）
  4. query() 返回嵌套列表，results["documents"][0] 才是结果，且已按相似度排好
  5. 我们手动用智谱算 embedding 再传给 ChromaDB，所以不会触发它默认的模型下载
  6. API key 应该放 .env，用 dotenv 加载 —— 从这课起告别硬编码

下一课预告

你现在有了一个能跑的 RAG，但代码是"一整坨脚本"：文档、切分、检索、生成都混在一个文件里。要变成一个真正的 MVP，还需要：

  • 把 RAG 流程封装成可复用的函数 / 类（ask(question) 一行调用）
  • 做一个交互式问答：命令行里持续提问，不用每次改代码重跑
  • 处理几个真实场景："文档里没有答案"该怎么办、检索结果不相关怎么办
