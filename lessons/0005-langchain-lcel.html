开篇：Week 1 你手写的，LangChain 想帮你打包

回到 Lesson 1 的 01_chat.py。你手写了三件事，然后手动串起来：

messages = [{"role": "system", ...}, {"role": "user", ...}]   # ① 拼消息
response = client.chat.completions.create(...)               # ② 调模型
answer = response.choices[0].message.content                 # ③ 抠答案

这三步哪一步都离不开另外两步，混在一个脚本里。LangChain 的想法很朴素：把这三件事各做成一块独立、可组合的积木，再用一行串起来。它没有做任何魔法——你 Week 1 手写过的每一步，框架只是给它穿了个马甲。

一一对照，就是这张表（本课的核心）：

Week 1 手写（01_chat.py）LangChain 积木角色
messages=[{"role":"system",...},{"role":"user",...}] ChatPromptTemplate.from_messages([...]) prompt 模板
OpenAI 客户端 + client.chat.completions.create(...) ChatOpenAI(...) llm 模型
response.choices[0].message.content StrOutputParser() parser 解析器
上面三步手动串 prompt | llm | parser chain 链
手动调用 + 手动提取 chain.invoke({"question": ...}) 触发

整节课就是把这张表从上到下实现一遍。学完你会清楚看到：框架的价值不是"更强大"，而是"更可组合"——因为每块都是独立积木，下节课你就能把 retriever（检索器）插到链最前面，重写整条 RAG。

🎯 为什么这对你的可信看板重要

可信看板的 AI 能力（文档问答、数据分析、版本评估）会越拼越多。如果每加一个能力都重写一个messages=[] + create() 脚本，很快就会复制粘贴成一团乱麻。LCEL 让你像搭积木一样组合能力——这正是工程化 AI 和"能跑的脚本"的分水岭，也是面试官想看到的思维。

知识 ①：Prompt Template —— 告别 f-string 手拼

Week 1 你用 f-string 拼 prompt（f"问题: {query}"）。能用，但 prompt 和数据焊死在一起——换个 query 就得重拼一次，也没法把它当成一个独立组件塞进链里。

LangChain 给你 Prompt Template：模板里写占位符，运行时再用实际数据填充：

from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "你是可信工程助手，帮助开发者理解编码规范和可信构建流程。"),
    ("user", "{question}"),     # {question} 是占位符，运行时才填
])

对照：占位符 {question} 之于模板，就是 f-string 里 {query} 之于格式串。区别在于模板是独立对象，可以复用、可以校验（少了哪个占位符会报错）、可以塞进链里。

💡 from_messages 的格式

传一个列表，每条消息是一个 (role, content) 元组：("system", ...)、("user", ...)、("assistant", ...)。这和你在 Lesson 0002 学的 messages 数组结构完全对应——role 换成了字符串，content 里多了占位符。本质没变。

知识 ②：LCEL 管道 —— 三块积木一行串起

三块积木都有了，LCEL（LangChain Expression Language）用 |（管道符）把它们按顺序串成一条链，就像 Unix 管道 cat | grep | sort：

from langchain_openai import ChatOpenAI
from langchain_core.output_parsers import StrOutputParser

llm = ChatOpenAI(model="deepseek-v4-flash", api_key=DS_KEY, base_url="https://api.deepseek.com", temperature=0)
parser = StrOutputParser()

chain = prompt | llm | parser   # ⭐ 数据流：模板 → 模型 → 解析

这一行的含义，从左到右读就是数据流向：

  {question: "..."}  →  prompt  →  llm  →  parser  →  "纯文本答案"
                     填模板          调模型          抠 .content

图 1：prompt | llm | parser —— 上一个积木的输出，自动喂给下一个

每个 | 之间，上一个积木的输出自动成为下一个积木的输入。你不用手写"把 prompt 的结果传给 llm"——LCEL 替你接好了管子。chain 本身的类型是 RunnableSequence（一组 Runnable 的串联）。

触发：统一的 invoke 接口

链定义好之后，调用只需一行，把占位符的值塞进一个字典：

answer = chain.invoke({"question": "什么是编码规范检查？用一句话解释。"})
print(answer)

invoke 接收一个字典，键就是模板里的占位符名（这里是 "question"）。它会自动流过整条链：填模板 → 调 DeepSeek → 抠出文本，最后 answer 就是一段纯文本字符串。

💡 每块积木都是 Runnable

关键在于统一接口：prompt、llm、parser、chain 每一个都有 .invoke() 方法（它们都实现了 Runnable 协议）。这就是为什么能随便用 | 串联——因为接口一致，任何积木的输出都能直接接另一个的输入。下节课你把 prompt 换成 retriever | prompt，整条 RAG 就拼出来了，几乎不用改后面。

⚠️ 一个小坑，先打个预防针

如果你好奇 print(type(answer))，会看到 TextAccessor 而不是 str——别慌。它是 str 的子类（isinstance(answer, str) 是 True），len()、.upper()、字符串拼接、打印全部照常。这是 langchain-core 1.x 的新行为，把它当普通字符串用就行。另外：官方说明 ChatOpenAI 针对 OpenAI 标准设计，DeepSeek 的标准 chat 完全可用（本课已端到端验证），但厂商私有扩展字段不会被保留——目前用不到，知道即可。

✅ 自检：看输出对不对

判断标准：

  • 打印出一句话回答（大意："编码规范检查是用静态分析工具扫描代码是否符合规范……"）→ ②④都填对，链跑通了。

  • TypeError: unsupported operand type(s) for | → ② 还没填（None | llm 报错），或 ④ 里写反了顺序。
  • KeyError: ... missing variables → ② 里占位符名和 invoke 字典的键对不上（比如写成了 {q}，但 invoke 传的是 "question"）。报错会告诉你缺哪个变量。

这四个错误，正好覆盖了那两行能犯的典型错——填对就说明你真的会了，而不是抄对了。

Week 2 路线：从这里出发

你现在握着三块可组合的积木和一个统一接口。Week 2 接下来就是不断换积木、加积木：

  • Lesson 0006（下一节）：把 Week 1 的整条 RAG 用 LCEL 重写——在链最前面插一个 retriever：retriever | prompt | llm | parser。你会看到相似度门控如何以 Runnable 的方式接进来，以及 Week 1 手写的 rag.py 怎么被几行 LCEL 替代。
  • Document Loaders + RecursiveCharacterTextSplitter：用框架替换你手写的 split("\n\n")，从真实文件（PDF、Markdown）加载文档。
  • Tool Calling：让 LLM 主动决定调用哪个工具——这是 Agent 的入口，也是可信看板"自动分析扫描数据"的起点。
